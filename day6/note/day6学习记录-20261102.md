# Day 6 学习记录｜从 MLIR 到 NPU，补齐 HFusion 输入的上卡验证

## 今天的进展

上次我已经能从 HIVM 层的 `add.mlir` 编出设备文件并在 NPU 上看到正确结果，但当时 host 程序的“比较成功”只是无条件打印，而且 HFusion 转换与上卡用的是两份不同输入。这次把两个缺口都补上了：host 现在检查 `rtKernelLaunch` 返回码，并在 C++ 中逐元素比较；一份新的 HFusion/Linalg 输入也确实经过转换、设备编译和上卡运行。

这里要把“跑通”的范围说准。HFusion 输入使用的是**源码构建的 `bishengir-opt` + CANN 包内的 `bishengir-compile`** 两段工具链，中间还用脚本抽出了 DEVICE 函数。它证明这份输入可以走到设备执行，尚不能证明包内单条 `--enable-hfusion-compile` 命令可用，也没有验证多个算子的融合效果。

## 一、HIVM VecAdd：把输出校验做实

原有 `vecadd/add.mlir` 直接处于 HIVM 层，设备编译仍得到 2648 B 的 `kernel.o`，全局符号为 `add`。host 侧在 `vecadd/main.cpp` 中新增了运行时返回码检查、逐元素比较和失败时的非零退出。两组各 16 个 int16 元素都通过：第一组是 `0..15 + 1 → 1..16`；第二组包含负数、零、正负抵消和 `32767/-32768` 边界输入，所有预期和均落在 int16 范围内。

为了确认校验不是只会报成功，还把同一 host 指向一个执行乘法的错误内核。IR 中能看到 `hivm.hir.vmul`，运行时 32 个元素里有 30 个与加法预期不符，程序退出码为 1。这个负例验证了当前 C++ 比较逻辑确实能发现错误结果。

| 检查 | 本次结果 | 证据 |
|---|---|---|
| HIVM 设备编译 | 2648 B ELF，符号 `add` | `logs/step6-compile-hivm.log`、`step6-artifacts.log` |
| host 构建与运行 | 两组共 32/32 匹配 | `logs/step6-host-build.log`、`step6-run-hivm.log` |
| 独立日志比较 | `NUMERIC_CHECK=PASS` | `logs/step6-numeric-check.log` |
| 乘法负例 | 30/32 不匹配，退出码 1 | `logs/step6-run-negative-control.log`、`hfusion-vecadd/mul-hfusion.device.hivm.mlir` |

## 二、同一份 HFusion 输入走到设备执行

新输入 `hfusion-vecadd/add-hfusion-host.mlir` 是 `tensor<16xi16>` 上的一条 `linalg.elemwise_binary{add}`。源码构建的 `bishengir-opt` 依次运行 HFusion 降低、转换到 HIVM、HIVM 优化；逐 pass 记录中可以看到它从 Linalg op 变为 `hivm.hir.load/load/vadd/store`。脚本随后从优化后的 IR 中去掉 HOST 包装函数，保留 DEVICE 入口及辅助函数，再用 CANN 包内编译器生成 2752 B 的设备 ELF，符号为 `add_single_outlined_0_0_0`。

同一个 host 程序加载这个 ELF 后，两组输入也是 32/32 匹配，独立日志比较再次得到 `NUMERIC_CHECK=PASS`。因此，相比 10 月 31 日的“HFusion 转换”和“HIVM VecAdd 上卡”两段分离的证据，现在有了**同一份 HFusion 输入到设备执行**的实测链路。不过输入只有一条逐元素 op；可以说 HFusion pipeline 与 outline 运行了，不能说已验证多算子融合。

| 阶段 | 本次结果 | 证据 |
|---|---|---|
| HFusion → 优化后的 HIVM | `linalg.elemwise_binary{add}` → `hivm.hir.vadd` 等操作 | `logs/step6-hfusion-conversion.log`、`step6-hfusion-passdump.log` |
| DEVICE 抽取与设备编译 | 2752 B ELF，符号 `add_single_outlined_0_0_0` | `logs/step6-hfusion-chain.log`、`step6-artifacts.log` |
| NPU 运行与数值比较 | 两组 32/32 匹配，`NUMERIC_CHECK=PASS` | `logs/step6-run-hfusion.log`、`step6-numeric-check.log` |

## 三、为什么用了两段工具链

在当前环境里，CANN 9.0.0 包内 `bishengir-compile 1.1.0` 对这份 HFusion 输入执行 `--enable-hfusion-compile` 时以 139 退出，崩溃日志指向 `HIVMAggregatedDecomposeOp`；交付包还记录了一个上游 HFusion 示例也会崩溃。源码构建的 `bishengir-opt` 能完成前半段 pipeline；包内编译器则能接受抽取出的 HIVM DEVICE 输入并生成 ELF，所以本次采用这两段工具链。交付报告还记录了源码构建的 `bishengir-compile` 与包内 `hivmc` 的选项兼容问题，但当前包中没有附上该失败的原始日志。

这说明**本机已试输入的包内 HFusion 单命令路径不可用**，不能据此断言所有 HFusion 输入都会崩溃，更不能把两段拼接说成产品默认的一条编译链。对应证据在 `logs/step6-packaged-hfusion-crash.log`、`step6-toolchain.log` 和 `hfusion-vecadd/build.sh`。

## 四、目前还有什么要改

1. **负例脚本的通过条件可以收紧。** `repro.sh` 目前把错误内核运行后的任意非零退出都记成 `NEGATIVE_CONTROL=PASS`。这次日志清楚显示了 30 处 mismatch 和退出码 1，因此本次结论成立；以后自动复现时应同时检查退出码和预期的 mismatch 文本，避免注册失败或崩溃也被算作“校验有效”。
2. **DEVICE 抽取脚本只适用于当前 IR 形态。** `extract-device-kernel.py` 按文本行识别 `func.func` 和结束括号，而非用 MLIR 解析器。对这份输入已经成功，但换成更复杂的函数体时应先检查抽取结果并做 IR 验证。
3. **验证范围仍小。** 当前只有单个 16 元素 int16 加法、两组数据、一台 910B3；没有不同 shape/dtype、真正的多算子融合或性能数据。`--target` 也未做不同取值对照。

## 这次学到的

这次最有价值的不是多得到一个 `kernel.o`，而是把“编译过了”“运行成功”“数值真的对”分成了三件可核对的事。现在能从同一份 HFusion 输入看到 Linalg op 经过 pass 变成 HIVM 的搬运与计算，最后形成 ELF 并在 NPU 上产生正确输出；也能用乘法负例证明 host 校验不是空打印。与此同时，工具链拼接、文本抽取和测试规模的限制都还在，后续实验应按这些边界继续补证据。
