## 0. 先把口径钉死

### 0.1 现在报告里的 Ratio 是怎么来的（已核对到源码与 bin）

1. `benchmarks/ops/bench_amin_fwd.py` → `ManifestBenchmark.profile` → msprof 采 kernel。
2. `benchmark_base.py` 优先读 msprof 产的 `visualize_data.bin`，取 CANN 自己算好的 roofline 条目
   （`title="GM/L2"` 且 `bw_name` 含 `GM Read + Write`）。
3. 该条目的四个量全部来自设备侧：
   | 量 | 来源 | Amin 实例 |
   |---|---|---|
   | duration | `OpBasicInfo.csv` Task Duration(us) | 14.64 µs（freq 1800 MHz，Block Dim 40） |
   | total_fops | `ArithmeticUtilization.csv`（cube 带 384 乘子）+ 每元素 ops | fp16 1.02 ops/elt；bf16 2.05 ops/elt |
   | total_bytes | `L2Cache.csv` 的 read_cache_miss_allocate × 128 B（**只算读，不算写**） | fp16 [2048,4096] = 16.77 MB |
   | computility | CANN 的 vec/cube 峰值 × 实测频率 | fp16 8.62 TOps/s |
4. `Ratio = Perf / min(AI × bw, computility)`，其中 **bw = CANN 表中的 1.75 TB/s**。
   （`msprof_roofline.py` 里的 `SOC_CONFIG["gm_bw"]=1.8` 只在 CSV fallback 路径 `compute_from_csvs` 用；
   实际走 bin 路径，所以报告恒为 1.75。此前的 1.8/1.75 不一致至此解释完毕。）

### 0.2 用户给出的口径（本文件采用）

```
Ratio = 实测性能 / min(理论最大计算性能, 理论最大带宽 × 实际 AI)
实测性能 = total_fops / 实测延迟
t_可达 = max(流量项, 发射项, 容量项)
```

- 流量项 = GM READ + WRITE 字节 / 可达带宽。
- 发射项 = 核启动时间 × op 数（设备侧；host 入队另算，约 216–450 µs，不进 kernel 时间）。
- 容量项 = 单核数据量 > UB(192 KiB) 时需要的搬运轮数。
- **小数据必须声明 L2 是否命中**；未命中且时间在几 µs 量级时，瓶颈是指令/流水，不是带宽。

### 0.3 可达带宽取值

| 依据 | 数值 | 说明 |
|---|---|---|
| 同机 1 GiB 拷贝实测（10 轮中位） | **1.20 TB/s** | fp16 1201.6 / bf16 1212.1 / fp32 1208.3 GB/s |
| 技能库 910B3 稳态基线 | **1.27–1.28 TB/s** | 512 MiB 对拍、纯 HBM |
| 本算子 fp16 16 MB 实测 | **1.15 TB/s** | 16.06 MiB/14.64 µs，已接近上面两档 |
| 理论 1.75 TB/s | 仅作对账 | 可达率 69–73% |

本文件用 **1.27 TB/s** 作大 shape 分母，并注明 1.20 的敏感性。

## 1. 四个 workload 的三项估算

原始数据取自 `reports/tileops/20261105_142216_660832_AminFwdOp/artifacts/msprof/*/OPPROF_*/`
的 `Memory.csv`（GM read/write）、`OpBasicInfo.csv`（时长/核数/频率）、`L2Cache.csv`（命中率）。

| # | shape / dtype / dim | 元素数 | GM 读+写 | 流量项 @1.27 | 容量项 | 发射项 | **t_可达** | 实测 | 达成率 |
|---|---|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | [2048,4096] fp16, dim=-1 | 8.39 M | 16.06 MiB | **13.3 µs** | 单核 402 KiB → UB 3 轮，已并入流量 | ~1.5 µs | 13.3 | 14.64 | **91%** |
| 2 | [2048,4096] bf16, dim=-1 | 8.39 M | 16.06 MiB | **13.3 µs** | 同上 | ~1.5 µs | 13.3 | 19.62 | **68%** |
| 3 | [64,32768] bf16, dim=-1 | 2.10 M | 4.01 MiB | **3.3 µs** | 单核 100 KiB → 1 轮 | ~1.5 µs | 3.3 | 7.50 | **44%** |
| 4 | [4,128,4096] fp16, dim=[0,2] | 2.10 M | 4.02 MiB | **3.3 µs** | 1 轮 | ~1.5 µs | 3.3 | 9.74 | **34%** |

- 与 1.20 TB/s 分母相比，达成率分别变为 100% / 75% / 48% / 38%——结论不变。
- **所有四例的 GM 读命中率 ≈ 0**（`L2Cache.csv` read_hit 每块 0–1，miss_allocate 1663/1666）。
  benchmark 每次迭代前刷 cache，单趟流式读，故 4 MB 虽装得下 L2 也拿不到 L2 带宽。
  → 小 shape 两例属于「未命中 L2 + 指令/流水受限」，不是带宽受限。

## 2. 结论：谁有真实头寸，谁是控制组

| 例子 | 现状 | 判定 | 调优空间 |
|---|---|---|---|
| 1 fp16 16 MB | 1.15 TB/s，91% 流量项 | **已贴顶** | ≤10%，只做回归控制组，不动 |
| 2 bf16 16 MB | 同流量却慢 34% | bf16 无原生向量 min，走 fp32 中转（G1） | **有 5–6 µs**：减指令数/去中转 |
| 3 bf16 4 MB | 0.56 TB/s，44% | 短 kernel + 每核仅 9 条 MTE2 | **有 ~2×**：加并发/加大搬运粒度 |
| 4 fp16 4 MB 跨维 | 0.43 TB/s，34% | 输出仅 128 个 → 核间负载不均 + 4×8 KB 跨 1 MB 跳读 | **有 ~2.5×** |

理论计算上限不构成约束：Amin 每元素 ~1 次 VALU 比较，AI≈0.5，
带宽项 (1.27×0.5=0.64 TOps/s) 比计算项 (8.6 TOps/s) 小一个量级；四例都是访存侧主导。

## 3. 对「实测口径」的落地建议

1. **主口径**：对每个 shape 用同进程、同 shape 的只读参照 kernel（`torch.amin(dim=...)`，或同流量纯拷贝）
   取 msprof 设备时间 `t_ref`，定义 `ratio_meas = t_ref / t_op`。
   这样 launch、L2 命中、核数、频率全部约掉，只剩 kernel 质量。
2. **本文件的简版**：`t_可达` 用流量项，`ratio_meas ≈ t_可达 / t_实测`（即上表达成率）。
3. **报告对账**：`ratio_theory = ratio_meas × (可达带宽 / 1.75)`。
   按 1.27 折算，四例为 90.2% / 67.3% / 44.0% / 33.9%，均值 **58.9%**（原 42.73%）。
4. **注意分母口径缺陷**：harness 的 `total_bytes` 只统计 L2 读 miss，不统计写。
   Amin 写只占 0.4%，影响可忽略；但 FusedAddRMSNorm 写=读，同样口径会把 AI 高估约 2×，
   ratio 被系统性压低——该算子跑之前必须先修这个口径。

## 5. 平均口径（2026-11-05 14:55 确认）

- **汇总**：等权算术平均 `mean = Σ Ratio_i / N`。**不按字节/耗时加权**，不挑 case。
- **判定**：只看这个平均是否 ≥60%，不要求每例单独 ≥60%。

  80% 的等价要求：之和 ≥320，对应读带宽 ≈1.48 TB/s > 实测稳态 1.27，理论口径下不可达。
