## 这次学的是怎样判断“改得有没有用”

前几天主要在验证算子能否生成、编译和算对。这次选的是 Amin，也就是沿指定维度求最小值。工作重点进入已有 NPU 实现的性能调优：让 Agent 根据 profile 提出候选，跑精度、性能和回归，再决定保留哪个版本。

这次仍采用 Developer 路径。既有整行能放入片上内存的 single-tile 实现，也有长归约轴需要分段处理的 tiled 实现。只盯着一个形状调参数容易得到片面的结果，所以最后用 manifest 中四个正式 workload 共同评估，smoke 不参与均值。

## Agent 阶段拿到了多少收益

下表统一采用交付包 `official-report/benchmark.json`、`report.md` 中的正式评测数据；迁移版数值来自包内阶段记录。时延是 msprof 设备侧口径，不是 Python 调用的墙钟时间。

| workload | 迁移版时延 | Agent 阶段时延 | 迁移版 Ratio | Agent 阶段 Ratio |
|---|---:|---:|---:|---:|
| `[2048,4096]` fp16 | 14.64 µs | 14.06 µs | 65.49% | 68.19% |
| `[2048,4096]` bf16 | 19.62 µs | 15.02 µs | 48.86% | 63.83% |
| `[64,32768]` bf16 | 7.50 µs | 7.12 µs | 31.96% | 33.66% |
| `[4,128,4096]` fp16，dim=[0,2] | 9.74 µs | 5.68 µs | 24.61% | 42.20% |
| **四例等权平均** | — | — | **42.73%** | **51.97%** |

两个 hidden-state 用例已经超过 60%，长归约轴和 3D 用例仍拉低均值。相对 60% 参考线，当前单算子均值还差 8.03 个百分点；但任务材料把 60% 写作“纯 Vector 类平均要求”，Amin 的四例均值不能直接代表整个类别的结果。Stage 4 gate 通过也只说明该阶段工件和检查符合门禁，不等于性能目标已经达到。

正式报告的正确性日志为 `14 passed`，`run.json` 中 benchmark 通过，profiler fallback、kernel filter fallback 和 invalid profile 计数均为 0。long-seq 在人读表中的 Kernel 一栏是 N/A，后续细查 kernel 级映射时仍应结合原始 profile，而不要只凭表格名称判断采样对象。

## 有效改动集中在两处

**一处是增大 3D 路径实际使用的 `block_m`。**Agent 在工厂内根据 UB 预算上调每块处理的输出行数，减少重复任务和小粒度写回。正式评测从 9.74 µs 降至 5.68 µs，约减少 41.7%。对应机制可以在 `kernel/final/_simple_reduce_kernel.py` 的 `_uplift_block_m` 和候选 `r2a_bmup` 记录里看到。

**另一处是把 bf16 结果的逐行转换改为整块向量转换。**归约仍需借助 fp32 中间结果；Agent 用一次 `T.vcast` 转换一块 `row_min`，替代 epilogue 中逐行的 `T.cast`。hidden-state bf16 从 19.62 µs 降至 15.02 µs，约减少 23.4%。这次收益明确落在输出转换路径，不能泛化成已经实现 bf16 原生归约。

长序列 tiled 路径的结构基本保持基线形态。报告里的 7.50→7.12 µs 是两轮正式评测差异，结合记录中的运行波动，暂不单独把它算作一项明确的结构优化收益。候选归因主要看 `kernel/opt_log.md` 与 `kernel/ab-logs/` 的交错对照。

## 看起来合理的优化，也可能更慢

Agent 还试过均衡分核、连续任务映射并合并 store、`T.Pipelined`、减小 tile_n，以及直线展开两个 tile 等方案。均衡分核和流水化没有稳定收益；连续映射在 bf16 对照中出现约 18.5% 回退；某些更大 tile 则超过 UB 容量。双 tile 直线展开还出现数值不匹配，记录将其定位到同一目标 buffer 的转换序列，最终没有采用。

这些结果让我认识到，减少某一种指令或让分核看起来更整齐，并不保证总时延下降。比如合并 store 同时改变了读地址分布；日志提出读局部性受损的解释，但这种微架构归因仍需对应的 profile 支持。编译器折叠等问题也应保留最小复现后再确认，暂不能据此说整个语言都做不了。

调优过程使用 A-B-B-A 交错测量，并保存多次 Task Duration。它比拿两次独立运行的最好数字比较更可靠。`perf_records.jsonl` 的 final 数据与正式 harness 报告略有差别，属于不同评测轮次；本文没有把两轮的最好数字拼成一张结果表。

## Ratio 的分母也要一起看

这里的 Ratio 衡量相对 Roofline 上限的表现，**51.97% 不表示比 PyTorch 快 51.97%**。材料追溯到 CANN profile 的 GM/L2 条目，报告显示带宽分母为 1.75 TB/s。它是模型参考值，不是本次测得的带宽；具体流量如何统计也会影响比例。原包记录了仅统计部分读流量的口径疑问，因此换算子时不能默认沿用同一个解释。

带宽标定中，大数据拷贝约达到 1.20 TB/s，小数据和批量调用的表现又不同。这说明数据规模、缓存与测量口径会影响可达值，但一次拷贝实验不是硬件性能上界的证明。因此原包“80% 物理不可达”的判断在本报告中不采用；后续可以补同 shape、同缓存策略和同设备计时口径的参照，再讨论目标是否合理。
