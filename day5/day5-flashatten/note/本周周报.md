# 第一周汇报

## 总结

这一周把 TileLang npuir 的三类 kernel 都跑了一遍**Vector 在 HBM 尺度与 torch 打平（1.000x / 1.008x）**，**Cube GEMM 4096³ 达到 104.71 TFLOPs（torch 的 0.38x）**，**MixCV FlashAttention 在 Developer 模式下跑通**（4 个形状正确性全过），**expert 版也通过 JIT 兼容层跑通 512/1024/4096**；FA kernel 设备时长 27.3–824.6 µs，512 时比 torch 三段式快 1.6x，4096 时慢 3.76x；当前首要怀疑是 64×64 小 tile，但还需 sweep 和流水 A/B 验证。

### 1.2 FA 数据流（expert 版代码，developer 版同构但按迭代流水）

```
GM: Q, K, V
   │ nd2nz (MTE2)
   ▼
L1: Q_tile, K_tile ──T.gemm (MTE1/M)──▶ L0C: S_tile
                                          │ fixpipe (FIX) + sync_block_set(i)
                                          ▼
                          GM workspace_1: S = QK^T  (seq × seq)
                                          │ sync_block_wait(i)
                                          ▼
                    AIV subid=0 / subid=1 各处理一半 M 行（UB）
                    vcast → vmul(scale) → reduce(max) → vmax(running)
                    → vsub → vexp → vcast(fp16) → reduce(sum)
                                          │ sync_block_set(i)
                                          ▼
                          GM workspace_2: P = exp(S - max)
                                          │ nd2nz
                                          ▼
L1: P_tile, V_tile ──T.gemm──▶ L0C: PV_tile ──fixpipe──▶ GM workspace_3[i]
                                          │ sync_block_wait(i)
                                          ▼
                    AIV×2: acc_o = acc_o * scale + PV
                          最后 vdiv(acc_o, logsum) → vcast → GM: O
```

### 1.3 两条流水的重叠（示意）

```
Cube   : [ S_0 ][ S_1 ][ S_2 ] ... [ S_n ]      [ PV_0 ][ PV_1 ][ PV_2 ] ...
Vector :        [ softmax_0 ][ softmax_1 ] ... [ softmax_n ][ acc_0 ][ acc_1 ] ...
                 └── 消费 S ──┘                    └── 消费 PV ──┘
         sync_block_set/wait 按 i 配对；GM workspace 两份时可再错开一拍
```

关键点：**Cube 与 Vector 不是同一份代码里的两条线程**，而是同一个 MIX module 里的
两个函数（expert）或被 CV Pipelining 拆出的两组 work item（developer）；
它们通过 GM workspace + flag 交接，天然可以并行。

| 天 | 负载 | 形状 / 口径 | ours | torch | 比值 | 备注 |
|----|------|-------------|------|-------|------|------|
| Day 3 | Vector abs | ≥256 MiB，HBM，10 轮 ABBA | 1.27–1.28 TB/s | 同 | **1.000x / 1.008x** | 128 MiB 那档不可复现，作废 |
| Day 3 | host 地板 | 任意小 kernel | — | — | — | 每次调用 216–232 µs；N=1M 设备仅 12.99 µs |
| Day 4 | Cube GEMM | 4096³，device | 1312.60 µs / 104.71 TFLOPs | 501.54 µs / 274.03 TFLOPs | 2.617x | K sweep 在 K≈1024 后进平台 |
| Day 4 | Cube GEMM | 16384²×64，device | 19.32 TFLOPs | 85.49 TFLOPs | 4.43x（单独）/3.70x（配对） | 超 L2，会话依赖 ±20% |
| Day 5 | FA（dev） | seq=512, dim=128, tile 64×64 | **27.33 µs / 4.91 TFLOPs** | 44.34 µs / 3.03 TFLOPs | **0.62x（我们快）** | 融合避免完整 S/P 跨算子物化 |
| Day 5 | FA（dev） | seq=1024 | 56.60 µs / 9.49 TFLOPs | 39.97 µs / 13.43 TFLOPs | 1.42x | 交叉点在 512–1024 |
| Day 5 | FA（dev） | seq=2048 | 208.61 µs / 10.29 TFLOPs | 93.91 µs / 22.87 TFLOPs | 2.22x | ours 饱和在 ~10 TFLOPs |
| Day 5 | FA（dev） | seq=4096 | 824.57 µs / 10.42 TFLOPs | 219.48 µs / 39.14 TFLOPs | 3.76x | 优先验证小 tile 假设 |

口径说明：
- Day 3/Day 4 是 device 时间（CANN `op_summary`），Day 5 也是；Day 5 的 e2e 另列在`day5学习指标.md` §1.3（0.42/0.45/0.63/1.28 ms，对 torch 1.40/1.45/1.91/3.60x）。
- 所有对拍都是同 session、同 dtype；FA 的 torch 基线是手写三段式，不是 SDPA。torch 那一列是 4 类 aclnn op、共 6 次设备任务的时长之和（2×matmul + softmax + muls + 2×cast），不是一条融合算子；所以 512 的 44.34 µs 里光 cast 就占 14.42 µs。
- FA 的 TFLOPs 按 `4·seq²·dim`（QK+PV）算；seq=512 时只有 0.28 TFLOPs 的 e2e 等效值，别和 device 列混。
- FA 的 tile 是 **64×64**：`block_K=32` 只是命令行参数，kernel 里 `T.gemm` 走满`dim=128`，这个维度没有生效（下一轮 sweep 不要再扫 block_K）。

### 本周最值得记住的三条规律

1. **小 kernel 只看 device，不看 e2e**：host 地板 230–450 µs，FA 512 的 kernel 只有 27 µs，e2e 的 1.40x 完全是 host 造成的，设备侧其实快 1.6x。
2. **融合的收益和 tile 的效率是两笔账**：512 时融合赢（不在独立算子间物化完整中间矩阵），4096 时当前实现只有 ~10 TFLOPs，被 torch 基线（39 TFLOPs）反超；64×64 tile 是首要假设，尚未由 sweep 证实。
3. **不同 regime 的指标不能混**：Vector 看 GB/s，Cube 看 TFLOPs，MixCV 要同时看device 时间和两条流水的重叠；`host_us` 只在小 kernel 上有意义。
