# amin_fwd 性能复核报告：实测最高是多少、瓶颈到底在哪

日期：2026-11-06
算子：TileOPs `amin_fwd`（reduce-min over last dim）
机器：Ascend 910B3（20 AI core / 40 AIV core），CANN 9.0.0，tilelang 0.1.2（dev root）
打分：`Ratio = 流量字节 / (Task Duration × 1.75 TB/s)`，四例等权平均
口径：每个数字都标来源。「**同口径实测**」= 出厂 kernel + msprof `--launch-count=20 --warm-up=5` 中位（A-B-B-A 取逐臂中位）。

---

## 0. 直接回答

**Q1：实测目前最高是多少？**

| 口径 | 四例平均 | 性质 |
|---|---:|---|
| 官方报告 | 51.97% | 每例**单次采样** |
| **同口径实测（出厂 kernel，逐臂中位）** | **51.6%** | 实测 |
| 逐例历史最好一次观测 | 53.5% | 实测**上界**，不可持续 |

单案例最高是 hidden fp16 的 **68.19%**（官方单次采样 14.06 µs）；同一份代码我方 5 对逐臂中位是 14.96 µs / **64.1%**。

> 原稿写的「52.9%」混了三种来源（官方单采样 + 我方中位 + 一个探针），见 §1.3，已更正。
> 更正后结论不变：**即使取逐例历史上界也只有 53.5%，离 60% 有 6.5 个点**。

**Q2：瓶颈在哪？**
4 MiB 那两个案例（long-seq 33%、3d 46%）的**52% 时间花在「启动 + 写 64–128 个 2 字节输出」这两项固定成本上**，
它们与数据量无关、与算法无关。16 MiB 那两个案例已经贴着带宽走（1.19 / 1.12 TB/s，实测上限 1.27）。
唯一有量的可动项是 long-seq 里 **2.2 µs 未与搬运重叠的计算**，而重叠在当前 toolchain 里不可表达。

## 1. 先把口径分开（否则数字会互相打架）

| 来源 | 性质 | 用途 |
|---|---|---|
| 官方报告 51.97% | **单次采样**（`sample_count=1`，min==max） | 出厂基准 |
| 我们 msprof `--launch-count=20` 中位 | 稳态 | 结构对比 |

2. **long-seq 的 Kernel 列是 N/A**：当次 roofline 条目按「时长最近」匹配 op，不是按 kernel 名过滤

3. **版本不同**：官方跑在 tilelang `0.1.1.10` / git `a83796be`；本文所有「我方数字」跑在 dev root

### 1.2 Ratio 不是测出来的，是算出来的（公式自证）

```
Ratio       = 流量字节 / (Task Duration × 1.75 TB/s)
流量字节    = 元素个数 × dtype 字节        例：2048×4096×2 = 16,777,216 B
Task Duration = msprof op 的 Task Duration(us)，--launch-count=20 --warm-up=5 取中位
1.75 TB/s   = 官方报告 Bandwidth 列记录的值（四例全为 1.7500）
```

**用官方原始报告反算，四例全部对上**（`infra-learning/day9/code/raw/amin_final_report_20261105.md`）：

| case | 官方 Latency | 官方 Ratio | 反算 `B/(t×1.75)` | 差 |
|---|---:|---:|---:|---:|
| hidden fp16 | 14.0600 µs | 68.19% | 68.19% | 0.00 |
| hidden bf16 | 15.0200 µs | 63.83% | 63.84% | +0.01 |
| long-seq bf16 | 7.1200 µs | 33.66% | 33.66% | 0.00 |
| 3d fp16 | 5.6800 µs | 42.20% | 42.19% | −0.01 |

→ **公式、字节口径（元素数×dtype）、分母 1.75 全部无误**。分母用的是 CANN roofline 的 1.75，
不是 `SOC_CONFIG["gm_bw"]=1.8`；910B3 也不在 `SOC_CONFIG` 表里，走的是 `DEFAULT_CONFIG`。

### 1.3 原稿的错：把三种来源拼成了一列「实测最高」

| case | 原稿取值 | 真实来源 | 同口径（出厂 kernel）应为 |
|---|---|---|---|
| hidden fp16 | 68.19% / 14.06 µs | **官方单次采样** | 14.96 µs → **64.1%** |
| hidden bf16 | 63.6% / 15.07 µs | 我方 5 对逐臂中位 | 63.6% ✓ 一致 |
| long-seq bf16 | 33.4% / 7.18 µs | **m11 探针（非出厂 kernel）** | 7.35 µs → **32.6%** |
| 3d fp16 | 46.1% / 5.20 µs | 我方 5 对逐臂中位 | 46.1% ✓ 一致 |

四例里两例取的是「别的来源的最好值」，拼出来的 52.9% 不对应任何一次可复现的实验。
**这就是你质疑的那个点：它是逐例取最优，不是测出来的。**

另一个细节错误：3d 的官方形状是 **[4, 128, 4096]**（4.19 MB），报告里写成 128×16384。字节数相同，形状标注已更正。

## 3. 瓶颈：long-seq 的加法阶梯（全部同会话、同几何实测）

这是全报告最有信息量的一张表。每一档只比上一档多做一件事，
所以差额就是**那一件事的边际成本**，可以直接相加、可以闭合：

| 档 | 内核里还有什么 | 中位 µs | **边际成本** | 占 wall |
|---|---|---:|---:|---:|
| ① null | 什么也不做 | 2.400 | **2.400** | **33%** |
| ② empty | + 写 64 个 2 B 输出 | 3.740–3.860 | **+1.34–1.46** | **19%** |
| ③ load | + 读满 4 MiB（零计算） | 5.060–5.260 | **+1.32–1.40** | 18% |
| ④ 真实 | + cast + reduce（与搬运串行） | 7.180–7.350 | **+1.92–2.30** | **30%** |

闭合校验：`2.40 + 1.40 + 1.32 + 2.23 = 7.35` ✓

**读四项**：

1. **启动 2.40 µs**：一个什么都不做的 40 块 kernel 的成本。它是「块调度 + 启动爬坡 + 收尾」，
   任何 kernel 都要付。它等于 long-seq 目标时间（3.99 µs）的 60%。
2. **写 64 个 2 B 输出 1.34–1.46 µs**：不是带宽（64 B 的带宽成本是 0），
   是每行一次 DMA 的**描述符 + 握手**成本，折合 **≈0.02 µs 每行 × 64 行**。
   这一项随「每块写几次」走，不随字节数走。
3. **读 4 MiB 只要 1.32–1.40 µs**：比纯带宽值（4.19 MB / 1.75 TB/s = 2.4 µs）还低，
   因为其中一部分已经藏在①的启动爬坡里了。**在这个尺度上字节近乎免费**。
4. **计算 1.92–2.30 µs**：vec 2.729 + mte2 1.699 + mte3 0.224 + scalar 0.483 = 5.135 ≈ aiv_time 5.002，
   即**四条 pipe 完全串行、零重叠**。这是唯一一处「本可以省掉」的成本。

**一句话**：`7.35 µs = 3.80 µs 固定成本（①②=52%） + 1.35 µs 数据 + 2.2 µs 未重叠计算`。

## 4. 每一项能不能动

| 成本项 | 能否压掉 | 依据 |
|---|---|---|
| ① 启动 2.40 µs | **不能** | 空 kernel 实测；属硬件/驱动固定成本 |
| ② 写 1.4 µs | **不能** | 试过「连续行映射 + 编译器合并写」，**+18.5% 回退**（r7）；试过 64 块（每块 1 行），8.22 µs（更差） |
| ③ 读 1.35 µs | **不能**，也无需 | 已低于纯带宽理论值，部分被启动爬坡吸收 |
| ④ 计算 2.2 µs | **理论能，实际不能** | 只能靠 MTE2/VEC 重叠；三条路全封（见 §5） |

结论：**52% 的墙属于不可压缩的固定成本，30% 属于被工具链锁死的计算，剩下 18% 是真实数据搬运。**

## 5. 为什么那 2.2 µs 压不掉（三条路逐一实测）

| 路径 | 实测结果 | 致命点 |
|---|---|---|
| 自动流水 `T.Pipelined(n, num_stages=2)` | 2 迭代、4 迭代生成的 `kernel.mlir` 与 `T.serial` **逐字节相同**，`memref.alloc=1`（无第二级缓冲） | 参数是纯 no-op，与有没有守卫无关 |
| 直线展开，手工排布多级 | 一个直线体**最多落地 2 个 compute site**；第 3 个起 `vcast`/`vreduce` 整段消失，**设备上 29/64 行静默错值**，编译零告警 | IR 生成层缺陷，不是调度问题 |
| Expert 模式 `set_flag`/`wait_flag` | 2 级形态错值；4 级形态把 AIV 跑挂（507034） | 不可用 |

补充一个反证：把两个 tile 的 DMA **都提到第一个 vcast 之前**发（循环内 2 个静态 site，正好卡在上限），
数值正确，但 `aiv 5.043 ≈ vec 2.786 + mte2 1.731 + mte3 0.268 + scalar 0.601`，**仍然零重叠**——
编译器在第一个 vcast 前插的是「等全部 MTE2」的屏障，提前发也换不到并行。

## 7. 那么最高能到多少（严格区分实测与假设）

| 口径 | 四例平均 | 性质 |
|---|---:|---|
| 官方报告 | 51.97% | 实测（每例单采样） |
| **同口径实测（出厂 kernel）** | **51.6%** | 实测（可复现） |
| 逐例历史最好一次观测 | 53.5% | 实测上界（拼接，不可复现） |
| 若 long-seq 计算完全重叠（其余不动，7.35→5.26 µs） | ≈54.8% | 假设，且该假设被 §5 否定 |
| 若四例同时命中最优（16 MiB 到 1.27 TB/s、两个 4 MiB 都到零计算地板） | 59.7–60.0% | 假设叠假设，**且它要求的事已被本节最小证明否定** |

**60% 不可达的最小证明**：

```
long-seq 过 60% 需要 4.194 MB / (0.60 × 1.75 TB/s) = 3.99 µs
实测「读满 4 MiB + 一个 cast 都不做」的内核        = 5.06 µs
两者相差 27%
而「连一个字节都不读、只写 64 个输出」的内核        = 3.74 µs（已经贴到 3.99）
```

也就是说：**把计算全部删掉、只保留必要的数据搬运，这个 kernel 仍然达不到 60% 所需的时间。**
任何正确的 kernel 只会更慢。

若按平均口径（用 §2 的同口径值 64.08 / 63.62 / 46.09 不动）：
long-seq 需要 `240 − 173.79 = 66.2%`，即 **3.62 µs**，而零计算地板是 5.06 µs——
**地板是它的 1.40 倍**。

## 8. 判定

按项目方法论（`t = t_aiv + launch_floor + wave_tail`，连续多个结构分支 blocked +
机制探针全 negative 即收尾）：

> **long-seq 记为 `[DESIGN_LIMIT]`。四例平均同口径实测 51.6%、
> 逐例取最优的上界 53.5%，60% 在当前 toolchain 下不可达。**

结论绑定 toolchain 版本戳。若上游补齐以下任一项，需重算：

- bf16 原生 `reduce_min` → long-seq 的 vec 由 2.7 降到 ~1.4 µs，wall ≈ 6.1 µs → 39%
- `T.Pipelined` 在 npuir backend 真正生成双缓冲，或直线体不再丢 compute site
- `atomic_min`（可把一行拆给多核，绕过波尾不平衡）

## 8.5 附录：人工阶段做了什么、证伪了什么

### 落地进代码的（2 项）

| 项 | 改动 | 验证 | 收益 |
|---|---|---|---|
| **m1b** | `few_wave = num_logical <= 2×vector_cores` 时，分核数从 40 改为 `num_logical` 的整除因子（3d：40→32），**去掉动态守卫**，任务循环的 `T.Pipelined` 才真正双缓冲 | 5 对 A-B-B-A，五对全负 | 3d 5.85 → 5.20 µs，**40.9% → 46.1%** |
| **门禁缺陷** | `--level boundary` 调用了不存在的 `_boundary_case`（实为 `_tiled_boundary_case`），长期静默跳过；改名后两例恢复执行 | L0 10/10、L1 10/10、L2 5/5、boundary 6/6 | 无性能收益，恢复覆盖率 |

### 被证伪的假设（9 条）

| # | 原假设 | 实测结果 |
|---|---|---|
| 1 | 给 `T.Pipelined` 加级数能换来重叠 | 2/4 迭代的 IR 与 `T.serial` 逐字节相同，`alloc=1` |
| 2 | 流水失效是因为循环里有运行时守卫 | 去掉守卫仍不生效；守卫不是原因，「2 次迭代没稳态」也不是 |
| 3 | site 被丢是因为两次 `vcast` 写了同一个 dst | 4 个**全去别名**的 site 仍只落地 2 个，与 dst 无关 |
| 4 | 直线展开 + 独立 work buffer 能做手工软流水 | 8 site 变体 IR 里 `vcast=1`；设备 **29/64 行静默错值** |
| 5 | 两个 DMA 提前发出，硬件就会重叠 | 数值正确，但 `aiv` = 各 pipe 之和，零重叠 |
| 6 | 64 块（每块 1 行）临界路径更短 | **8.220 µs**，比 32 块慢 14%（两波） |
| 7 | bf16 保序映射成 int16 后原生 reduce 更快 | **慢 2.9 倍**（vec 7.33 → 18.34） |
| 8 | 连续行映射 + 合并写出能省写侧成本 | **+18.5% 回退**；写侧是每行描述符/握手成本，不可合批 |
| 9 | 3d 可以照搬 32 块无流水几何 | **8.680 µs**（出厂 5.20），`mte3` 单项 3.728 µs |

另有一条「未证成」而非证伪：专家模式手工双缓冲理论上能到 ~5.9 µs，
但 2 级错值、4 级 AIV 挂死——是**被工具链堵住**，不是被数据否定。

### 方法上的三条自我修正

1. **3 对 A/B 会造假信号**：m1b 在 hidden fp16 先报 −20%，5 对复核后是 tie（−1.19%, p=1.0）。
   本算子在 13.0–17.2 µs 双稳态，**≥5 对才能裁决 5% 量级**。
2. **msprof 对子进程崩溃仍返回 0**：m6m 的坏臂 `--check` 64/64 全错，profile 却照常出中位数，
   且 `vec` 恰好减半，看起来像「重叠成功」。**先过 `--check`，再看时间。**
3. **两个 60% 门槛一度混用**：long-seq 自己过 60% 要 **3.99 µs**；要让四例平均到 60%
   （其余三例不动）要 **3.64 µs**。本报告统一用 3.99 µs 作单案例门槛。
