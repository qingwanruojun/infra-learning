## 2. 为什么超不过 60%

### 2.1 先把 60% 翻译成时间

`Ratio = B/(t×1.75)`，要平均 60%，就得四例的 `t` 同时满足下表（B 和 1.75 都动不了）：

| case | 60% 所需延迟 | 现状最好 | 缺口 |
|---|---:|---:|---:|
| hidden fp16 | 15.98 µs | 14.06 | 已达标 |
| hidden bf16 | 15.98 µs | 14.64 | 已达标 |
| long-seq bf16 | 3.99 µs | 7.10 | **−3.11 µs** |
| 3d fp16 | 3.99 µs | 5.06 | **−1.07 µs** |

即：两个 16 MB 的 case 已经过线（甚至接近 aiv 上界），**全部缺口压在两个 4 MB 的小 case 上**——
而它们的延迟大头根本不是数据搬运，而是核没吃满、波没叠上。

### 2.2 三张天花板，逐层剥开

用官方 msprof 的分项算（`aiv_time` = 单核忙时，`dur − aiv` = 空转+发射）：

| case | dur | aiv | launch 地板 | 波边界延迟 |
|---|---:|---:|---:|---:|
| hidden fp16 | 14.06 | 11.51 | 0.7 | 1.85 |
| hidden bf16 | 15.02 | 13.49 | 0.7 | 0.83 |
| long-seq bf16 | 7.12 | 5.13 | 0.7 | 1.29 |
| 3d fp16 | 5.68 | 3.62 | 0.7 | 1.36 |

- **天花板 A（把发射与空转全部抹掉，`t = aiv`）**：83.3 / 71.1 / 46.7 / 66.2 → 平均 **66.8%**。
  这是"kernel 一发射就满负荷、零空隙"的极端上界，物理上不存在，但它已经说明：
  **80% 在本口径下不可能**（四例里两例的 aiv 上界只有 46.7% 和 66.2%）。
- **天花板 B（只把波边界延迟消掉，保留 0.7 µs 发射地板）**：78.5 / 67.6 / 41.1 / 55.5 → 平均 **60.7%**。
  也就是 **60% 恰好等于"跨波流水"这一项补齐后的账面**——一步之遥，但这一步不是调参。
- **天花板 C（再叠加 bf16 原生归约，去掉 fp32 中转）**：估算 **~65%**。
  bf16 的两例 vec 分别是 7.32 µs（fp16 同形体只要 2.67）和 2.70 µs（占 long-seq 核内时间 54%）。

### 2.3 三把锁，每把都是一个语言缺口

1. **波边界延迟消不掉 —— CG-2026-0020**
   `T.Pipelined` 在循环体含运行时守卫时**静默降级为串行**，不生成双缓冲、也不告警。
   实测：带守卫的流水版与串行版的 `vec`/`mte2` 分项**逐位相同**；去掉守卫后同一 kernel
   每任务核内时间 1.64 → 1.38 µs（−16%）。
   这就是 3d 能拿到 −11.1%、而 hidden/long-seq 拿不到的根本原因。
2. **bf16 没有原生算术 —— 只能 fp32 中转**
   `T.reduce_min` / `T.vmin` / `T.min` / `T.vbitcast` 的 bf16 全部不支持（docs 规格表逐一亲读）。
   于是每读一个 bf16 tile 都要 `vcast` 成 fp32 再做规约，UB 占用翻倍、vec 时间翻倍以上，
   直接导致 long-seq 的 UB 预算装不下第二个缓冲（也就装不下双缓冲流水）。
3. **行不能拆给多核 —— 无 `atomic_min`**
   只有 `T.atomic_add`。long-seq 是 64 行 / 40 核 = 1.6 波，尾巴 16 个核空转；
   想把一行拆成两半给两个核再合并 min，没有原子 min 就只能在两阶段 kernel 里绕，
   而两阶段要多一次发射（0.7 µs 地板 × 2），得不偿失。

另有 **CG-2026-0019** 封住了手工绕路：直线展开里同一 dst 的两次 `T.vcast` 会被
CSE 折成一次（"先算者赢"），所以手工写"copy(t+1) 与 cast/reduce(t) 交错"必然错值。
自动流水（CG-2026-0020）和手工交错（CG-2026-0019）两条路同时被堵，这才是 plateau 的实质。

### 2.4 一句话

**这个算子的 52–54% 不是"调得不够"，而是当前 TileLang npuir 能力下的结构上界**：
16 MB 的两例已经贴着 HBM 与核内时间跑（68.2% / 65.5%），
4 MB 的两例卡在"核吃不满 + 波叠不上 + bf16 要 fp32 中转"。
要越过 60%，需要的不是更多轮调参，而是三个原语：
**守卫下的真流水（CG-2026-0020）、bf16 原生规约（reduce/vmin/bitcast）、atomic_min**。
80% 则与硬件和口径同时冲突（aiv 上界平均仅 66.8%，long-seq 单例上界 46.7%）。
