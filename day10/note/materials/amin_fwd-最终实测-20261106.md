## 1. 背景：这个算子测的是什么

### 1.1 算子本身

`amin` 是"沿某一维取最小值"的归约。测试用的四个用例，是把输入压成二维后**每一行求最小值、输出一个数**：

| 用例 | 输入形状 | op 参数 | 内核实际处理 | 读取字节 | 输出字节 |
|---|---|---|---|---|---:|
| hidden fp16 | 2048 × 4096 | `dim=-1` | 2048 行 × 4096 列 | 16.78 MB | 4 KB |
| hidden bf16 | 2048 × 4096 | `dim=-1` | 2048 行 × 4096 列 | 16.78 MB | 4 KB |
| long-seq bf16 | 64 × 32768 | `dim=-1` | 64 行 × 32768 列 | 4.19 MB | 128 B |
| 3d fp16 | 4 × 128 × 4096 | **`dim=[0, 2]`** | **128 行 × 16384 列** | 4.19 MB | 256 B |

> **3d 用例的形状容易看错。** `dim=[0,2]` 的意思是"把第 0 维和第 2 维归约掉、保留第 1 维"，
> 所以输出是 128 个数，内核看到的是 **128 行 × 16384 列**（= 4×4096 拼成一行），
> **不是** 512 行 × 4096 列。这一点决定了它只能用 `block_m=1`，详见 §5.3。
>
> 早期文档里把它写成 128×16384 的"字节数对、行数错"版本，现已更正。

### 1.2 评测指标 Ratio

```
Ratio = 流量字节 / (Task Duration × 1.75 TB/s)
```

| 符号 | 含义 | 取值 |
|---|---|---|
| 流量字节 | 元素个数 × dtype 字节数（只算读，输出可忽略） | 见上表 |
| Task Duration | msprof 测得的**内核**耗时（不含 Python 提交开销） | 实测 |
| 1.75 TB/s | 官方 Roofline 报告的 Bandwidth 列，CANN 表值 | **不是** `SOC_CONFIG["gm_bw"]=1.8` |

**它的物理含义**：假设这块卡的理论带宽是 1.75 TB/s，一个完美实现应该在 `字节/1.75TB/s` 的时间内跑完。
Ratio 就是"完美实现的时间 ÷ 实际时间"。

所以 **Ratio 的天花板不是 100%**：小张量根本喂不满带宽，启动、握手、写输出这些固定成本会把分母撑大。
`60%` 这个目标，对 4.19 MB 的两个用例来说本身就极其苛刻（详见前置文档的"零计算地板"证明）。

## 2. 测量口径：数字是怎么来的

这一节很重要，因为**同一个 Ratio 用不同口径能差出好几个百分点**，历史上已经因此出过两次错。

### 2.1 唯一采用的内核耗时口径

```bash
msprof op --kernel-name=main --launch-count=20 --warm-up=5 ...
```

- 采集 20 次真实内核执行的 `Task Duration(us)`，**取中位数**；
- 前 5 次是预热，不计入；
- 只统计被 `--kernel-name` 选中的主内核，跳过 mask / cast 等辅助内核。

### 2.2 官方 harness 内部已经取过一次中位

官方入口是：

```bash
pytest benchmarks/ops/bench_amin_fwd.py -sv -m "not smoke"
```

它在内部调用 `--launch-count=10 --warm-up=5`，并取 10 次的中位数
（`tileops/benchmark/msprof.py:708`，`latency_us = median_us`）。

**所以一次 harness 跑出来的数字，已经是"run 内中位"了。** 剩下的抖动全部来自**跨 run**：
操作系统、频率、内存布局、其他进程。这一点是理解 §3 的前提。

### 2.3 禁止的三种混用

| 混用 | 后果 | 本次是否犯过 |
|---|---|---|
| 官方报告的单次值 vs 我方中位 | 把运行间波动当成版本差异 | 犯过，已更正 |
| 端到端耗时 vs 内核耗时 | 把 Python 提交成本（百微秒级）算进内核 | 未犯 |
| 假设值 vs 实测值 | 报出一个没有任何 kernel 跑出过的数字 | 犯过（早期 55.4%），已删除 |

### 3.2 逐例分布（11-06 六次）

| 用例 | 六次实测 | 中位 | 时延范围 | 稳定性 |
|---|---|---:|---|---|
| hidden fp16 | 69.77 / 57.96 / 59.84 / 67.04 / 64.60 / 67.51 | **65.8%** | 13.74–16.54 µs | 差，**双稳态** |
| hidden bf16 | 59.11 / 64.34 / 59.77 / 61.61 / 64.17 / 59.92 | **60.8%** | 14.90–16.22 µs | 差，与 fp16 部分反相 |
| long-seq bf16 | 32.57 / 33.01 / 32.04 / 32.92 / 33.01 / 32.13 | **32.7%** | 7.26–7.48 µs | 好，±1 pp |
| 3d fp16 | 45.39 / 43.42 / 46.09 / 46.63 / 43.58 / 44.06 | **44.7%** | 5.14–5.52 µs | 好 |

**整体波动几乎全部来自两个 hidden 用例。** 它们各自的耗时在快/慢两个状态之间跳，
而且经常**反相**：第 5 次 fp16 是 69.77% 而 bf16 只有 59.11%，第 6 次反过来（fp16 57.96%、bf16 64.34%）。
这不像随机噪声，更像两者在争同一个资源。

long-seq 和 3d 两个 4.19 MB 的用例则非常稳，六次分别只差 1 pp 和 3 pp。

### 3.3 怎么报这个数

| 场合 | 建议写法 |
|---|---|
| 正式交付 / 对外 | **Ratio = 51.0% ± 1.3**（九次中位 ± 极差的一半） |
| 需要强调最好成绩 | 单次最高 **52.05%**，但必须注明"抽样上界，不可复现" |
| 禁止 | 直接写 52.05% 而不提中位；或用一次跑的 49.44% 说"性能回退" |

> **为什么不能只报最高值**：52.05% 只比中位高 1.07 个百分点，而跨 run 极差是 2.61 个百分点。
> 换句话说，**这个 1.07 完全在噪声里**——它不代表任何代码差异，只代表这一次抽签运气好。

## 4. 结果二：Ratio 公式验证（12/12 全中）

### 4.1 验证方法

不是"照着公式算一遍看着像"，而是**从 harness 的原始输出里把 `latency_us` 抠出来，
套公式反算 Ratio，再和 harness 自己打印的 `Ratio(%)` 逐行比**。两者来自同一次运行的同一份数据，
所以任何口径错误都会立刻暴露。

### 4.2 验证结果

| 次 | 用例 | Task Duration (µs) | 流量字节 | 反算 Ratio | harness 打印 | 差值 (pp) |
|---|---|---:|---:|---:|---:|---:|
| 8 | hidden fp16 | 14.30 | 16,777,216 | 67.04% | 67.04% | 0.002 |
| 8 | hidden bf16 | 15.56 | 16,777,216 | 61.61% | 61.61% | 0.003 |
| 8 | long-seq | 7.28 | 4,194,304 | 32.92% | 32.92% | 0.002 |
| 8 | 3d fp16 | 5.14 | 4,194,304 | 46.63% | 46.63% | 0.001 |
| 9 | hidden fp16 | 14.84 | 16,777,216 | 64.60% | 64.60% | 0.002 |
| 9 | hidden bf16 | 14.94 | 16,777,216 | 64.17% | 64.17% | 0.000 |
| 9 | long-seq | 7.26 | 4,194,304 | 33.01% | 33.01% | 0.003 |
| 9 | 3d fp16 | 5.50 | 4,194,304 | 43.58% | 43.58% | 0.001 |
| 10 | hidden fp16 | 14.20 | 16,777,216 | 67.51% | 67.51% | 0.004 |
| 10 | hidden bf16 | 16.00 | 16,777,216 | 59.92% | 59.92% | 0.001 |
| 10 | long-seq | 7.46 | 4,194,304 | 32.13% | 32.13% | 0.002 |
| 10 | 3d fp16 | 5.44 | 4,194,304 | 44.06% | 44.06% | 0.002 |

**12 行、3 次独立运行、4 个不同形状，全部 ≤0.004 pp。**
公式、带宽常数（1.75 而非 1.8）、字节口径（元素数 × dtype 字节）三项同时被钉死。

### 4.3 反算的第二个用途：探测器「混口径」

反算不只能验证公式，还能**反过来发现别人给的数有问题**。收到的这样两行就是一个例子：

| 行 | 时延 | Ratio | 反解出的流量字节 |
|---|---:|---:|---|
| 初始 | 158.32 µs | 0.7578% | 2,099,561 B ≈ **2.00 MiB** |
| 当前 | 8.62 µs | 27.8189% | 4,196,481 B ≈ **4.00 MiB** |

矛盾在哪：

- 时延加速了 **18.37×**（158.32 ÷ 8.62）；
- 但 Ratio 涨了 **36.71×**（27.8189 ÷ 0.7578）。

**同一个张量上，Ratio 必须严格按 `1/时延` 变化，这两个倍数必须相等。** 现在差 2.00×，
而反解出的字节数正好也是 2 MiB vs 4 MiB——对上了。也就是说**这两行根本不是同一个张量**，
不能并排当作"加速比 + Ratio 涨幅"来读。

如果它们确实是同一个 4 MiB 的 workload，那么初始那行应该是：

```
4,194,304 / (158.32e-6 × 1.75e12) = 1.514%
```

报告里的 0.7578% 正好是它的一半。这种"正好差一半"最常见的三个成因：
① 用元素个数当字节数（bf16 只按 1 B/元素 算）；
② 只算了读或只算了写，没算完整流量；
③ 分母用了 3.5 TB/s（1.75 的两倍）。

### 4.4 自查口诀

```
bytes = Ratio × t × 1.75e12
```

**能还原成整数 MiB（4,194,304 / 16,777,216 …）就是对的；还原不出来，就是口径错了。**
这一条已经写进 skill。

## 5. 结果三：几何扫描，默认配置已是最优

### 5.1 为什么要扫、怎么扫

`bench_amin_fwd.py` 在构造算子时**不传 `block_m` / `tile_n`**，几何完全由内核自己的
`AminFwdKernel.default_config` 启发式决定。所以修改这个启发式属于**合法的内核优化**
（没有改动 workload、没有针对 benchmark 特判），值得一试。

`default_config` 目前的两个分支：

- **单 tile 路径**（`N` 能整个放进 UB）：在 `[1, 2, 4, 8]` 里挑**装得下的最大** `block_m`；
- **分 tile 路径**（`N` 太大）：挑**让 N 方向 tile 数最少**的 `block_m`。

注意它优化的是"**tile 数**"，不是"**波次**"。这留下一个理论缺口：可能存在"tile 数稍多，
但块数正好整除 40 个核"的配置更快。本节就是去验证这个缺口。

扫描方式：

```bash
msprof op --kernel-name=main --launch-count=20 --warm-up=5 \
    python sweep_bm.py --workload <case> --bm <block_m> --tn <tile_n>
```

- 每个配置 20 次 launch 取中位；
- 每个配置跑 2–3 轮，**轮内随机顺序**（避免某个配置总在第一个/最后一个跑，吃到时钟效应）；
- 每个配置都必须先通过数值校验（与 `torch.amin` 逐行比对，`max_diff = 0`）。

### 5.2 long-seq bf16（M=64, N=32768，默认 `block_m=1 / tile_n=16384`）

| block_m | tile_n | 各轮中位 (µs) | 相对默认 | 判定 |
|---:|---:|---|---:|---|
| **1（默认）** | 16384 | 7.22 / 7.28 | — | **基准 7.25** |
| 2 | 16384 | 7.18 / 7.40 | −1% / +2% | 打平 |
| 4 | 16384 | 7.29 / 7.43 | +1% / +2% | 打平 |
| 8 | 16384 | 7.25 / 7.40 / 9.28 | 0% ~ +28% | 打平（末轮有外部干扰） |
| 2 | 8192 | 8.86 / 8.97 / 11.64 | **+23%** | 明显变慢 |
| 4 | 8192 | 8.84 / 9.18 | **+24%** | 明显变慢 |
| 8 | 4096 | 11.67 / 11.88 | **+62%** | 明显变慢 |

**读法**：`block_m` 从 1 加到 8（块数从 64 降到 8），耗时没有任何改善；
而只要在 N 方向切 tile，就立刻变慢，且**切得越碎越慢**。

### 5.3 3d fp16（M=128, N=16384，默认 `block_m=1`）

| block_m | 六次中位 (µs) | 判定 |
|---:|---|---|
| **1（默认）** | 5.46 / 5.63 / 5.61 / 5.56 / 5.53 / 5.58 → 中位 **5.57** | 基准 |
| 2 | 5.63 / 5.32 / 5.33 / 5.54 / 5.60 / 5.55 → 中位 **5.55** | 打平（−0.4%） |
| 4 | 编译失败 | **UB 溢出**：需 1,573,120 bit > 可用 1,572,864 bit，**只差 32 字节** |

**这里有个方法论教训的现场**：第一批只跑了 3 对，结果 `bm=2` 比 `bm=1` 快 5%（5.33 vs 5.61），
看起来是个真信号。补到 6 对后，差距消失（5.55 vs 5.57）。

> **3 对只能判方向，5 对以上才能定量。** 这条纪律写在 skill 里，这次又被自己的数据验证了一遍。

`bm=4` 只差 **32 字节**就装得下，很诱人——它能把 128 个逻辑块压成 32 个、正好一波做完。
但要省出这 32 字节，必须改内核的 buffer 分配，属于用"改代码的正确性风险"换"未知的收益"，
在 `bm=2` 已经证明无收益的前提下不值得做。

### 5.4 hidden fp16（M=2048, N=4096，默认 `block_m=4`）

| block_m | 各轮中位 (µs) | 判定 |
|---:|---|---|
| **4（默认）** | 14.31 / 16.47 / 14.39 → 中位 **14.39** | 基准 |
| 8 | 15.44 / 15.96 / 15.02 → 中位 **15.44** | **慢 7%** |

`bm=8` 能把每核 13 轮任务降到 7 轮，理论上是好方向，但实测反而慢 7%——
说明这个尺寸下瓶颈不在任务轮数，而在每轮的数据搬运效率（UB 翻倍后 bank 冲突/多缓冲膨胀）。

### 5.5 三条可复用的结论

**结论 1：N 方向切 tile 一律变慢，与 tile 大小无关。**

long-seq 的 N=32768：切成 4 片（`tile_n=8192`）慢 23–24%，切成 8 片（`tile_n=4096`）慢 62%。
原因是每轮 tile 都是一次**独立的 DMA 握手**，固定开销与传输量无关。
这和"写 64 个 2 字节输出要花 1.4 µs"是同一条成本曲线——
在小张量上，**握手次数比字节数更重要**。

**结论 2：`Block Dim` 在同一 workload 内不随 `block_m` 变。**

| 用例 | Block Dim |
|---|---:|
| long-seq（各种 `block_m`） | 恒为 40 |
| 3d（`block_m`=1 或 2） | 恒为 32 |

这意味着：改 `block_m` **并没有改变内核的发射形状**，只是把每个块的活变多/变少。
`bm=2` 时逻辑上只有 32 个活块，但硬件仍按 40 起，多出来的块靠 `if block_id < num_logical` 守卫空转，
**空转的块照样付 launch 成本**。

这解释了一个早期困惑：手写的"32 块 kernel"探针测到 7.20 µs，
但走配置路径的 `bm=2/tn=8192` 实测是 8.86–9.18 µs。两者不是同一件事。

**结论 3：扫参之前先看 `Block Dim` 列。**

如果它不随你扫的参数变化，说明参数没碰到发射形状，**收益上限基本为零**。
这一条写进 skill，可以省掉大量无效扫描。

| 第二次更正（11-06 15:00，本节） | 「落地了，但在四个用例上一次都不触发，收益为 0」 | ✅ |

### 6.2 定案依据

第一次更正错在哪：我去 grep 了 `amin_fwd_kernel/_simple_reduce_kernel.py`（根目录那份），
发现没有 `few_wave`，就下了结论。**但那份是死代码。**

正确的查法是问 import 链：

```bash
python -c "from tileops.kernels.reduction.amin_fwd import amin_fwd as A; \
print(A._simple_reduce_kernel.__module__)"
# 输出：tileops.kernels.reduction.amin_fwd.amin_fwd_kernel.perf_opt._simple_reduce_kernel
```

**活的是 `perf_opt/` 那份**——`amin_fwd.py:95` 直接导入它，绕过了包 `__init__.py`。
根目录同名文件只有包 `__init__` 引用，算子根本不走。

| 事实 | 证据 |
|---|---|
| 活文件含 `few_wave` | `inspect.getsource` 可见；mtime 11-05 **20:26** |
| 官方报告早于 m1b | 官方 run_id `20261105_190051`（19:00 起跑）< 20:26 |
| 根目录同名文件是死代码 | 只被 `amin_fwd_kernel/__init__.py` 引用 |
| `perf_opt/_simple_reduce_kernel_tiled.py` 只是壳 | 2 KB，再导出自 `_simple_reduce_kernel` |
| **四个 benchmark 形状都不触发** | 条件：`非 bf16` ∧ `逻辑块数 ≤ 80` ∧ `不能整除` |
| `ab_3d_final5` 的 B 臂就是出厂版 | A=`m2a_tiled_pipe.py`（5.85 µs）vs B=出厂（5.20 µs），出厂本来就快 |

### 6.3 为什么"落地了却没收益"

`few_wave` 的作用是：当逻辑块数不能被 40 整除时，把块数降到一个**能整除的约数**，让每个核负载均衡。
它的触发条件是：

```
非 bf16（long-seq 被排除）
逻辑块数 ≤ 2 × 40 = 80（3d 是 128 块，hidden 是 512 块，都被排除）
逻辑块数不能被默认块数整除
```

**四个用例，一条都不满足。** 所以这段代码在本次评测里是纯粹的"存在但不生效"。

**净结论**：迁移之后真正进代码的只有「门禁修复」+「一段不触发的 `few_wave`」，
**性能收益为 0**。52.05% 不是任何一次优化的结果，它就是迁移版本本身的水平。

## 附录 A：术语表

| 术语 | 含义 |
|---|---|
| **Ratio** | `流量字节 / (内核耗时 × 1.75 TB/s)`，见 §1.2 |
| **Task Duration** | msprof 测得的内核执行时间，不含 Python 提交开销 |
| **block_m** | 一个逻辑块处理多少行。`block_m=4` 表示每块一次处理 4 行 |
| **tile_n** | N 方向的切分粒度。`tile_n=16384` 表示一次搬 16384 列；`0` 表示不切 |
| **逻辑块数** | `ceil(M / block_m)`，例如 128 行 / `block_m=1` = 128 个逻辑块 |
| **Block Dim** | 硬件实际启动的块数（msprof 的列）。与逻辑块数不一定相等 |
| **UB** | Unified Buffer，每核 192 KiB 的片上缓冲。装不下会编译报 `ub overflow` |
| **波次** | 逻辑块数 ÷ 40 个核。超过 1 波意味着有的核要串行多做几轮 |
| **pp** | 百分点（percentage point）。68% → 70% 是 +2 pp |
| **MiB** | 1,048,576 字节。4 MiB = 4,194,304 B，本次两个小用例的流量 |
| **tie** | 差异落在测量噪声内，不判方向 |
| **双稳态** | 同一个用例在两次运行间稳定地落在两个不同耗时档，而非连续抖动 |
| **零计算地板** | 保留全部数据搬运、删掉全部计算后测得的耗时，是任何正确实现的下界 |
